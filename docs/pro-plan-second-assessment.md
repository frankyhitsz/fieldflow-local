# `pro-plan.md` 第二轮核查

核查日期：2026-08-24
对照基线：`73fac30`

这份记录只描述已经查到的代码和可重现结果。`pro-plan.md` 中的产品路线有参考价值，但不等于当前系统的缺陷清单。

## P0 结论

| 编号 | 结论 | 处理和证据 |
| --- | --- | --- |
| P0-01 紧急工单在重排失败时消失 | 确认，已修复 | 紧急工单现在先独立提交 D 修订，再启动重排。失败会保留工单和上一个 V，并把该 V 标记为 `PARTIAL_NEW_DEMAND`。同一幂等键重试返回原 Run 和失败，不重复写入。回归测试覆盖失败、重试和重启。 |
| P0-02 历史恢复覆盖整个业务场景 | 风险确认，已拆分语义 | 原行为是上轮明确选定的“完整快照恢复为新版本”，不是无故出现的实现错误。本轮将其拆为重新激活、克隆场景和显式业务回滚。回滚需要差异预览、确认令牌、原因和预期 D，默认禁止重开已完成工单或删除后续新增工单。 |
| P0-03 用计划时间推断不可移动工单 | 确认，已修复当前边界 | 求解器和 Verifier 现在共享持久化 `PlanningContext`。自动冻结只依据明确的 started/completed 事实；计划到达或出发时间只产生警告。真实 `EN_ROUTE` 仍需要未来的执行事件模型。 |
| P0-04 派生字段可被候选伪造 | 确认，已修复 | 新的 `ScheduleNormalizer` 从场景、来源方案、PlanningContext 和行程模型重建行程、SLA 延迟、`changed`、`locked`、解释、证据、KPI 和业务评分。Verifier 独立重算并拒绝不一致候选；发布事务内再校验一次。 |

## P1 结论

| 编号 | 结论 | 处理和边界 |
| --- | --- | --- |
| P1-01 Run/Candidate 非原子完成 | 确认，已修复 | `complete_schedule_run` 在同一 SQLite 事务中插入 Candidate 并结束 Run；唯一索引保证一个 Run 只有一个 Candidate。触发器故障注入证明任一写入失败时两边同时回滚。 |
| P1-02 幂等未覆盖所有版本动作 | 确认，已修复主流程 | baseline、optimize、replan、历史激活、克隆、业务回滚和实验发布都使用场景+动作命名空间和请求指纹。同键同请求返回原资源，同键不同请求返回 409。 |
| P1-03 校验后再 `strip()` | 确认，已修复 | 名称、标签、ID、备注、颜色和幂等键在 Pydantic 约束中先去空白再校验。Patch 现在区分 omitted 和 null；空 Patch 不再白白增加 D，只有备注和突发上报时间允许显式清空。 |
| P1-04 TravelTimeProvider 没有贯穿主路径 | 确认，已修复计算链 | baseline、优化、重排、诊断、证据、KPI、Normalizer 和 Verifier 都可使用同一 provider。不对称矩阵测试覆盖求解与校验一致性。行程 provider 还没有变成用户可编辑配置。 |
| P1-05 普通优化和重排是同步长请求 | 确认，本轮延期 | 现有前端依赖同步返回 Schedule，改成 202 会破坏接口契约。硬取消 OR-Tools 还需要独立进程而不是只加队列状态。当前保留 30 秒上限和发布防护，不用占位端点假装已异步化。 |
| P1-06 实验队列和生命周期不足 | 确认，已修复当前边界 | profile 去重且最多 8 个，队列最多 4 个，满载返回 429。增加 `CANCEL_REQUESTED`、`CANCELLED`和 `COMPLETED_WITH_ERRORS`，每个策略前后检查取消。全部不可发布时标记失败。显式保存 winner Candidate 和 Plan。取消是策略之间的协作式取消，不会硬终止正在执行的 OR-Tools 调用。 |
| P1-07 跨快照比较可能误导 | 确认，已修复 | 比较结果返回是否可比、快照一致性、共同需求和增删改摘要。不同快照时不返回目标差异，页面不给出优劣或改善百分比。同时修复了基准目标为 0 时的除零显示。 |
| P1-08 工作状态机太小 | 属于真实产品缺口，不是本轮可安全单点修补的 bug | 当前 pending/started/completed 仅适合演示，但状态已保证单向，已执行工单的业务字段不能改写。引入 dispatch/accept/depart/arrive 需要动作端点、事件时间、行为人、幂等和 UI 一起上线，本轮没有只加枚举。 |
| P1-09 导入模块即创建 Store | 确认，已修复导入副作用 | Store 和实验 worker 在 FastAPI lifespan 中创建和关闭。子进程测试证明单纯 `import backend.main` 不创建数据库。应用工厂可注入不同 Store，顺序启动可隔离数据。当前 Store 绑定仍是进程级，不支持同一进程内并发服务多个 app。 |
| P1-10 SQLite 历史无界增长 | 容量风险成立，未在本轮执行破坏性重构 | 当前演示数量没有已发生容量故障的证据。快照去重、retention 和 prune CLI 需要先定义保留政策，否则容易删除可追溯记录。v1 旧历史重建是前一轮用户明确选择，且有时间戳备份，不是静默删除。本项保留为下一个 Schema 工作包。 |
| P1-11 前端状态表达不完整 | 部分确认 | 动态时间轴、次日时间、多出发点、轮询 AbortController 和地图键盘操作在基线中已存在，所以“均缺失”不成立。本轮补了部分覆盖、实验取消/部分成功/唯一获胜者、不可发布候选不参与推荐。完整的 focus trap 和 OpenAPI 类型生成仍未实现。 |
| P1-12 本地 Web 安全边界 | 部分确认，已补高收益边界 | 默认绑定 loopback，新增 TrustedHost、严格浏览器 Origin 检查和报告文件名清洗。报告对用户文本做 HTML 转义并有测试。启动 token 需要同步改前端、CLI 和 API 兼容契约，本轮没有强行引入。报告未默认脱敏，文档已明确数据敏感性。 |
| P1-13 缺少 LICENSE | 确认，需仓库所有者决定 | MIT 和 Apache-2.0 有不同法律效果。本轮不替所有者选择许可证，也不在包元数据中写一个不存在的 SPDX 标识。 |

## M0–M4 任务书

M0 中的 FF-301–FF-306 已落到代码和回归测试。FF-307 的主要失败、并发、迁移和伪造路径已覆盖，没有额外引入 Hypothesis 依赖。

M1 中的应用启动副作用、计算链上的行程 provider、输入契约、实验治理和部分本地安全已处理。统一子进程求解队列、快照去重、保留政策、启动 token 和完整依赖注入仍是后续架构工作。

M2–M4 主要是产品扩展和发布治理：收件箱、现场执行事件、拖拽编辑、导入导出、休息/区域/团队约束、成本模型、容量规划、不确定性仿真、真实 Benchmark 和开源治理。它们不是静态审查后可以默认上线的“合理化补丁”，需要单独的业务优先级、数据和验收口径。

## 本轮额外发现

- 重排时点晚于技师班次+加班上限时，OR-Tools 原会因无效 `SetRange` 抛出 500。现在该技师被视为没有剩余容量，返回正常诊断。
- 幂等请求指纹对容器内的 Pydantic 对象不是递归序列化，已修正。
- 策略页原会把不可发布候选的低分当成“推荐”，现在只在可发布集合内选最低分。
- 空的工单或技师 Patch 原会创建没有业务变化的新 D，现在返回 422。
- 对比页在基准目标值为 0 时可能显示无穷百分比，现在明确显示不可计算。
- 突发工单入库后如果连初始重排准备都失败，命令原会留在中间状态并在重试时再次运行。现在准备失败也会保存结构化终态，同键重试不再运行求解器。
- 业务回滚的幂等重试原会被回滚自己产生的新 D 拒绝。现在先用来源 V 和原请求指纹查找已发布方案，再做当前 D 校验。
- Store 发布事务的最终校验原仍固定使用默认行程模型。现在 Store 持有注入 provider，API 的求解、标准化、候选验证和发布事务复核都使用它。
- 11px 的次要文字中仍有多处灰色对比度不足，已统一使用对比度更高的文字令牌；表单、场景选择和重排输入继续保持 14px/36px 下限。
