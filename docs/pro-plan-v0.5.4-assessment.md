# `pro-plan.md` 复核记录（v0.5.5）

复核基于本地代码、SQLite 迁移样本、API/组件/E2E 流程和故障注入，不把审查文档中的推测直接当作事实。状态中的“后续”表示建议合理，但需要新的运行架构、业务数据或仓库所有者决策；本次没有用空模型或不可运行的入口冒充完成。

## P0

| 项目 | 结论 | 处理 |
| --- | --- | --- |
| P0-01 A 重放绕过校验 | 合理，已修 | POST 重放、GET、列表、直接接口、retry、rerun 和风险比较都从同一个校验读取路径取 A；失败记录不再返回 result。 |
| P0-02 删除证明字段可降级 | 合理，已修 | Schema v18 增加关系型 `attestation_requirement`。新记录只能是 `REQUIRED`，触发器禁止业务写入或改成 `LEGACY_MIGRATED`；旧记录由迁移显式标记。 |
| P0-03 重排分析范围不一致 | 合理，已修 | 重排统一为 `PUBLICATION_REMAINING_PLAN`，成本、容量、风险排除已冻结的开始/完成任务，并使用相同排程签名。普通 V 使用 `FROZEN_FULL_PLAN`。 |
| P0-04 空未来路线忽略 route entry | 合理，已修 | 尾部追加从冻结路线入口的位置、可用时间和返回点开始，即使当前没有未来 assignment。 |
| P0-05 无关技师缺勤算扰动 | 合理，已修 | 缺勤“发生”和由缺勤造成的未服务、SLA、加班损害分开；用同 trial 无缺勤结果计算因果差值。 |
| P0-06 突发时间和空闲技师错误 | 合理，已修 | 突发时点不早于分析/发布时间；事件先独立生成，再由方案选择技师。空闲技师也计算出发、服务、返程和加班。 |
| P0-07 retry 预留后崩溃卡死 | 合理，已修 | 命令使用 `RESERVED → ANALYSIS_RESERVED → COMPLETED`，启动只对账分析命名空间；A 绑定前崩溃可用相同键继续。 |

## P1

| 项目 | 结论 | 处理 |
| --- | --- | --- |
| P1-01 清单未证明完整输入/错误 | 合理，已修 | `DecisionInputManifest` 绑定请求、政策、上下文、Plan、runtime、快照、排程和旅行模型；result/failure manifest 分别绑定成功结果或结构化错误。 |
| P1-02 retry 未复核完整输入 | 合理，已修 | exact retry 复核原 input manifest、runtime/build、发布上下文、快照、排程和旅行模型；漂移时拒绝并要求 current rerun。 |
| P1-03 哈希不证明真实性 | 结论正确，但不是当前安全承诺 | SHA-256 清单用于本地一致性和篡改检测，不是签名、远程证明或多用户防恶意管理员机制。威胁模型继续明确该边界。 |
| P1-04 缺 RuntimeManifest | 合理，已修 | 保存 Python、OR-Tools、SQLite、Pydantic、OS、架构、build SHA 和依赖声明指纹。 |
| P1-05 风险比较缺配对区间 | 合理，已修 | 同 trial 输出差值均值、95% 配对置信区间和 win/tie/loss。 |
| P1-06 风险比较不可审计 | 合理，已修 | 新增持久 `RiskComparisonRun`，绑定两个 A、共同场景集和比较哈希。 |
| P1-07 A 在同步 HTTP 内计算 | 合理，后续 | 当前 trial 和时限均有上限，A 有持久终态与中断恢复，但没有独立 worker/lease/硬取消。完整解决需要 FF-1220～FF-1223，不能靠后台线程假装可靠。 |
| P1-08 rerun-current 无幂等键 | 合理，已修 | rerun-current 强制 `Idempotency-Key`，重复请求返回同一新 logical A。 |
| P1-09 外包缺供应商承诺 | 合理，部分修复 | `ExternalAssignment` 明确 `capacity_verified=false`、未承诺开始/完成时间和 `UNVERIFIED_ASSUMPTION`；界面醒目标明不能当现场承诺。真正验证需要供应商容量数据。 |
| P1-10 容量成本来源含糊 | 合理，已修 | 新技师显式选择工资、固定费或两者；外包费用只从成本政策或容量政策二选一，并保存来源。 |
| P1-11 实验公式只有版本号 | 合理，已修 | 实验冻结完整公共评价政策快照并纳入 fingerprint，候选统一用该快照重算。 |
| P1-12 公平求解与排名不完全相同 | 合理，部分修复 | KPI 增加归一化负载最小/最大值，排名继续使用归一化 range；OR-Tools 的 span 仍按服务维度，统一整数归一化目标属于求解模型改版。 |
| P1-13 旅行时间仍为静态 | 事实正确，不是隐藏能力 | 当前 provider 明确是静态欧氏网格模型；时间参数属于接口契约，不宣称实时路况。时间依赖矩阵需要新的数据来源。 |
| P1-14 “时间窗”只约束开始 | 语义正确，界面已澄清 | 业务契约是“允许开始窗口”，UI 和验证错误均按开始时刻描述；服务允许在窗口结束后完成不是现有模型缺陷。 |
| P1-15 active_booking_ids 不是 Booking ID | 合理，已修兼容路径 | 执行事件和冻结身份传播真实 Booking ID；只有迁移前没有 Booking 的记录才回退 source assignment hash。 |
| P1-16 actual_late_start 字段名不准 | 合理，已修兼容路径 | 新增 `customer_window_late_start_minutes` 和 `planned_start_variance_minutes`；旧字段只保留反序列化兼容。 |
| P1-17 默认剩余时间固定 15 分钟 | 合理，后续 | 开始服务可提交预计剩余分钟；没有现场更新时使用明确的 15 分钟政策。自动估计需要进度或工单类型历史，不能凭计划值伪造。 |
| P1-18 active plan 双重权威 | 合理，已修 | `plan_applicability` 是权威投影；触发器与启动对账同步 `scenarios.active_plan_version_id` 缓存。 |
| P1-19 重命名修改冻结 JSON | 合理，已修 | 名称、备注和标签迁入 `plan_metadata`；PlanVersion 发布 payload 不因重命名变化。 |
| P1-20 单一 D 混合三类变化 | 合理，后续 | 当前 D 仍是本地操作员可理解的单一业务修订。拆分规划/执行/元数据水位会改变全部冲突协议，归入 FF-1226。 |
| P1-21 跨快照返回 KPI 差值 | 合理，已修 | 快照不同时所有 delta 返回 null，只保留 A/B 原值和工单、技师变化摘要。 |
| P1-22 哈希缺规范版本/Unicode/排序 | 部分合理，已修可安全部分 | 规范升级为 V2并做 Unicode NFC。路线、assignment 等列表顺序具有业务语义，不能全局排序；无序实体的领域级排序继续逐项处理。 |
| P1-23 迁移可能丢历史/Artifact | 合理，关键路径已修 | 修复旧唯一约束重建时 Artifact 未复制的问题，并用含真实 Artifact 的 v14 样本验证哈希、数量、FK。v1 历史重建是已确认的一次性决定，仍先做时间戳备份；无效父记录进入 quarantine。 |
| P1-24 损坏 JSON 拖垮启动/列表 | 合理，主要路径已修 | 启动用 `json_valid` 隔离并登记损坏记录；A、Artifact、Plan 解析错误返回稳定 409，不再成为 500 或静默可信结果。 |
| P1-25 模块级 Store/executor/锁 | 合理，后续 | 测试可注入 Store，但完整生命周期和依赖注入需要拆分 `main.py` 与 worker 运行时，归入 FF-1224。 |
| P1-26 人工改派锁不回收 | 合理，已修 | 使用带引用计数的 `RLock` 条目，请求结束后回收。 |
| P1-27 取消不能终止 OR-Tools | 合理，后续 | 当前取消能阻止后续候选/发布，不能中断已进入 C++ 的调用。可靠硬取消需要独立求解子进程。 |
| P1-28 重复快照无保留策略 | 合理，后续 | 本地数据库规模受 fixture 和操作量约束；自动清理会破坏审计历史，须先定义保留/导出/压缩政策。 |
