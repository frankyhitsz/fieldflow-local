# `pro-plan.md` 复核记录（v0.5.6）

本记录针对 2026-08-25 变更后的审查文档。结论来自当前代码、SQLite 故障注入、API/组件测试和完整构建；网页审查无法观察本地运行状态的部分没有直接照单全收。“后续”表示建议本身合理，但需要改变已确认的单机同步架构、引入真实外部数据或由仓库所有者作法律/治理决定。

## P0

| 项目 | 裁决 | 实际处理 |
| --- | --- | --- |
| P0-01 信任不向下传播 | 合理，已修 | Plan、A、Artifact、RiskComparison 都返回 self/parent/effective trust；父级 FAILED 或 Legacy 不能被子记录洗成 VERIFIED。A 在有效信任失败时移除 result，比较结果标记不可用于业务。 |
| P0-02 Plan Manifest 绑定不足 | 合理，已修 | Manifest V2 绑定关系型身份、不可变头、来源/稳定性谱系、Candidate、发布上下文、验证 Artifact 和排序后的 Plan Artifact 清单。读取时交叉核对 ID、场景、编号和创建时间。 |
| P0-03 Plan 消费路径 fail-open | 合理，已修 | 统一 `require_plan_for_use` 覆盖执行、分析、发布重放、人工改派、克隆、恢复、比较、版本/通用报告及 schedules 投影。Legacy 只读，FAILED 只供审计。 |
| P0-04 剩余计划重复整班/多日成本 | 合理，已修 | remaining 强制单日；PAID_SHIFT 拆分完整日已承诺人工与发布后剩余增量，且没有剩余任务的技师增量为零。容量使用同一成本范围。 |
| P0-05 未验证外包显示为可执行 | 合理，已修安全语义 | 未接入供应商承诺时状态为 `EXTERNAL_CONDITIONAL`，`feasible`、正式 KPI 和经济建议为空，只保留条件上界、待确认工单和诊断证据。没有凭空创建“已确认供应商”。 |
| P0-06 应急未进入 SLA 总体 | 合理，已修 | 分开发布承诺 SLA 和全部需求 SLA；应急进入全部需求分母，并报告应急完成、准时和未服务概率。 |
| P0-07 RUNNING 绕过终态证明 | 合理，已修 | A 的 status、started/finished、lease 字段写入关系型列；RUNNING 必须有 ReservationManifest，关系型终态触发器禁止回退，JSON 与列不一致直接失败。 |

## P1

| 项目 | 裁决 | 实际处理或边界 |
| --- | --- | --- |
| P1-01 比较不复核 A/Artifact | 合理，已修 | 比较保存双方 A manifest、trial 与 scenario-set Artifact ID/哈希；GET 每次重新验证。 |
| P1-02 比较缺幂等且哈希含生成字段 | 合理，已修 | 强制 `Idempotency-Key`；语义输入/结果哈希排除 ID、编号、创建时间。预检提前到两次子分析之前，相同键不同请求无副作用地返回 409。 |
| P1-03 Legacy 默认可用 | 合理，已修 | Legacy Plan/A 不参与默认业务结果。Legacy Plan 的重新认证创建新 V，旧 payload 和 D 不变。 |
| P1-04 Plan 关系型身份未交叉验证 | 合理，已修 | ID、scenario、number、created_at 与 payload 逐项校验并纳入 Manifest V2。 |
| P1-05 Artifact 忽略父 A | 合理，已修 | Artifact 返回 `self_integrity`、`parent_analysis_integrity` 和 `effective_integrity`；父 A 失败时有效信任失败。 |
| P1-06 公共 Python 函数可绕过 A | 部分合理，门禁已加强 | 决策函数现在要求 V2 有效 Plan 和完整发布清单；HTTP 业务路径仍强制持久 A。保留纯函数是测试和离线模型复用契约，不把它描述成审计 API。 |
| P1-07 应急响应人按计划而非 trial 进度 | 合理，已修 | 每个 trial 用已实现的随机行程、服务、no-show 进度计算候选技师可用时间。 |
| P1-08 应急去程无扰动且不进 SLA | 合理，已修 | 应急去程使用 keyed travel 随机扰动，应急准时结果进入 all-demand SLA。 |
| P1-09 remaining assumptions 文案过时 | 合理，已修 | 成本、容量、风险说明都明确“发布时剩余计划”和一次性日内范围。 |
| P1-10 空闲技师仍收 PAID_SHIFT | 合理，已修 | remaining 增量只计仍有排程的技师；完整日承诺单独列示。 |
| P1-11 规划指纹混入优先级/VIP/罚金 | 合理，已修 | assignment-feasibility 指纹只保留技能、位置、时长、允许开始窗口、reported_at、技师可行性、锁和旅行；目标字段单独分类。 |
| P1-12 备注/显示字段使计划失效 | 合理，已修 | 元数据不清空 active 也不标 stale；商业/目标字段保留 active 但提示数据变化；可行性字段执行原失效规则。 |
| P1-13 “时间窗”实际是开始窗口 | 合理，已澄清 | 编辑器和详情使用“允许开始时间/最晚开始时间/允许开始窗口”；内部字段为兼容保留。服务完成 SLA 另有明确截止字段。 |
| P1-14 超时服务固定剩余 15 分钟 | 与当前主路径不符 | 开始服务可显式提交预计剩余时长；未提交时，持久执行上下文使用该工单 `service_duration`，不是固定 15 分钟。15 分钟只保留为缺失执行上下文的可配置防御性策略。 |
| P1-15 Booking 不是正式聚合 | 合理，后续 | 当前执行事件有稳定 Booking ID 和冻结身份，但完整生命周期、改约/取消/通知需要新业务实体，归入 v0.7.0。 |
| P1-16 Provider 忽略 departure time | 事实正确，已公开限制 | 现有欧氏和矩阵 provider 是静态模型。保留时间参数是未来接口契约，不宣称实时路况；实现时变旅行需要版本化数据。 |
| P1-17 浮点坐标作为矩阵身份 | 合理，后续 | 当前内置欧氏模型没有碰撞问题；外部矩阵导入需要正式 Location ID 与校验，不能用字符串格式化补丁假装解决。 |
| P1-18 公平求解与公共评分不完全一致 | 合理，后续模型升级 | 排名按班次归一化负载范围，OR-Tools 仍优化服务分钟 span。异长班次下并非同一目标，不能声称已统一；需要新的整数归一化 Routing 目标和基准。 |
| P1-19 同步 HTTP 运行求解/A | 合理，非本版目标 | 审查任务自己把 Job Queue 列为 v0.6.0 且明确本轮 non-goal。当前有上限、持久状态和重启中断记录，但不伪装成异步 worker。 |
| P1-20 紧急单缺 Outbox | 合理，后续 | 当前本地流程没有外部消息目标；可靠重试队列与 Outbox 一起在 v0.6.0 实现。 |
| P1-21 线程取消不能终止 OR-Tools | 合理，后续 | 当前取消阻止后续候选/发布；硬取消必须使用独立求解子进程。 |
| P1-22 启动迁移有历史清空分支 | 事实成立但产品前提遗漏，已加强 | v1 清空重建是用户此前确认的迁移决定。现在先做时间戳 SQLite 备份，并把 schedules/plans/artifacts/experiments/publication keys 每行复制到 quarantine ledger 后才重建，不再无证据删除。 |
| P1-23 损坏记录阻塞列表 | 合理，关键路径已修 | 场景、Plan、A 列表隔离无法解析记录；Plan/场景列表返回跳过数，隔离索引可查询。全表离线 health CLI 仍属于 v0.6.0 运维范围。 |
