# FieldFlow Local

面向维修、安装与维保团队的本地派单和排程系统。它把技能、客户时间窗、SLA、技师班次、人工锁定与突发工单放进同一个可解释计划中；业务数据、二维坐标和求解过程均可离线运行。

## 快速开始

```bash
make setup
make demo
```

打开 [http://127.0.0.1:8000](http://127.0.0.1:8000)。如果 8000 已被占用，可运行：

```bash
make demo PORT=8001
```

首次打开不会自动创建方案，避免仅浏览页面也消耗版本号。推荐演示流程：

1. 点击“生成基线”，创建公开版本 V001；
2. 选择策略并点击“生成推荐方案”，对比 SLA、行程、加班和未分配工单；
3. 编辑工单、锁定技师或登记突发工单，再执行局部重排；
4. 在“方案版本”中打开、命名、比较或恢复任意历史版本；恢复会生成新版本，不覆盖原历史；
5. 在“策略实验室”中用 8/60 或 12/100 固定数据集批量比较策略，人工选择候选后发布；
6. 导出与指定版本绑定的静态 HTML 调度报告。

## 版本语义

- `V001`：公开方案版本。只有成功生成、重排、恢复或发布方案时增长。
- `D001`：业务数据修订。工单、技师和人工锁定发生变化时增长。
- 内部基线、实验候选、失败和取消的求解使用内部 ID，不占公开版本号。

每个公开版本保存完整业务快照、最终排程、策略、KPI、求解状态和来源关系。恢复历史版本会同时恢复业务快照与排程，但以一个新版本发布，因此后续历史不会丢失。

## 策略实验室

内置均衡、完成率优先、准时优先、低行程、低加班、工作量公平和稳定重排策略，并支持保存自定义权重。跨策略不比较各自的原始目标值，而是使用统一业务公式重新评价完成率、SLA、行程、加班和公平度。

内置六套固定种子场景：

- 正常主场景：4 名技师 / 24 个工单；
- 技能不足；
- 时间窗冲突；
- 突发工单重排；
- 策略实验中型：8 名技师 / 60 个工单；
- 策略实验压力型：12 名技师 / 100 个工单。

## 架构

```text
React + TypeScript 调度台
          │
        FastAPI
  ┌───────┼─────────────┐
贪心基线  OR-Tools  解释/诊断/版本快照
          │
        SQLite
```

- `backend/scheduler.py`：确定性基线、带时间窗的 OR-Tools 路由、KPI 与局部重排。
- `backend/storage.py`：业务修订、公开版本、完整快照、策略配置及实验持久化。
- `backend/main.py`：排程、恢复、比较、报告、策略和业务编辑 API。
- `frontend/src/App.tsx`：调度工作台、墨线地图、技师时间轴与交互状态流。
- `frontend/src/Management.tsx`：方案版本、技师管理、运营复盘和编辑器。
- `frontend/src/StrategyLab.tsx`：多策略实验、自定义权重与候选发布。
- `tests/`：硬约束、版本事务、恢复、并发、策略差异、API 流程和可读性测试。

## 求解语义

复杂车辆路径在时间限制内返回的方案显示为 `FEASIBLE` 或 `TIME_LIMIT`；系统不会把未证明全局最优的结果标成 `OPTIMAL`。未分配工单始终带原因码和可操作建议。局部重排会保留已开始或已执行工单的技师、顺序与执行时间，并使用稳定性代价约束其余变更。

## 验证与常用命令

```bash
make test          # 后端、API、版本事务与策略验收
make test-frontend # React 组件与渲染安全测试
make build         # TypeScript 检查 + Vite 生产构建
make demo-check    # 基线→优化→锁定→突发重排→比较→报告
make test-e2e      # Playwright 主流程与 200% 缩放检查
make verify        # 执行全部发布门禁（含 E2E）
make demo          # 构建并启动完整应用
```

API 文档位于 [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)。本地数据保存在仓库根目录的 `fieldflow.db`，数据库、迁移备份、虚拟环境、依赖目录和构建产物均已排除在 Git 提交之外。
