# FieldFlow Local

FieldFlow Local 用来安排一天内的上门维修、安装和保养任务。输入工单、技师班次、技能和客户可上门时间后，它会给出路线、时间表、未分配原因和主要指标。坐标、路程估算和数据都保存在本机。

## 运行

```bash
make setup
make demo
```

启动成功后，终端会显示访问地址，默认是 <http://127.0.0.1:8000>。如果 8000 端口已被占用，可以换一个端口：

```bash
make demo PORT=8001
```

需要查看或试调接口时，打开 <http://127.0.0.1:8000/docs>。

每次运行的数据都写在项目根目录的 `fieldflow.db` 中。这个文件只留在本机，不会进入 Git；迁移备份、虚拟环境、`node_modules` 和前端构建目录也一样。

## 先试一遍

首次打开时还没有方案，这是正常的。按下面的顺序可以走完一遍主要流程：

1. 在“今日调度”生成基线，得到 V001。
2. 选择一个策略并生成推荐方案，查看它和基线的差别。
3. 锁定一个工单，新增突发单，再做局部重排。
4. 到“方案版本”比较两个版本，重新激活与当前数据一致的旧方案，或把历史快照克隆成新场景。
5. 到“策略实验室”比较多种策略，选中一个候选后发布。
6. 到“运营复盘”读取已有分析，选择周期后再生成成本、风险或容量测算；每次新输入会保存为 A001、A002 等分析记录。
7. 从当前方案或版本页打开 HTML 报告。

## V、D 和 A

- `V001` 是方案版本。生成基线、优化、重排、重新激活历史方案、显式回滚数据或发布实验候选时，各增加一次。
- `D001` 是业务数据修订号。工单、技师或锁定关系改动时增加。
- `A001` 是经营分析记录。成本、容量或风险测算开始前分配；成功、失败和中断都会留痕。相同输入会复用已有运行中或已完成记录；失败和中断记录需要点“重试”生成下一次 A，原记录不会被覆盖。
- 实验候选和计算失败不会占用 V 号。

每个 V 版本都带有当时的工单、技师、锁定关系和排程。历史页把三种操作分开：

- “重新激活”只适用于业务数据没变的历史方案，不改工单和技师。
- “克隆场景”会从历史快照建立一个独立场景，原场景不变。
- “回滚业务数据”会先列出差异，再要求回滚原因和确认。它会创建新 D 和新 V，不删除原有历史。

历史列表可以按动作、策略和求解状态组合筛选。回滚确认会同时说明工单、技师、锁定关系和当前方案安排的变化。克隆出来的场景执行“恢复初始数据”时，会回到该副本创建时的历史快照。

紧急工单会先保存，再尝试重排。如果重排失败，工单仍在当前数据中，最后发布的方案会标记为“新需求未覆盖”。

## 策略实验

内置策略包括均衡、覆盖率优先、准时优先、低行程、低加班和工作量公平。做局部重排时还可以选择“稳定优先”。如果这些策略不合适，也可以保存自己的权重和计算时限。

各策略的权重不同，求解器给出的原始目标值不能直接横向比较。实验页会用统一公式另算“对比得分”，并分别标出计划覆盖、计划准时率、行程、加班和工作量表现最好的候选。

实验最多同时排队 4 个，可以取消。个别策略失败时，已成功的候选仍可比较和发布；一次实验只能选定一个正式方案。

## 经营测算

运营复盘以公开 V 的完整快照为输入，不读取后来修改的工单，也不会新增 D 或 V。进入页面只读取已有 A，用户点击生成后才写入新记录。A 保存执行水位、分析时点、政策、算法版本、构建 SHA 和完整输入指纹。

- 成本按整数分计算，正常人工、加班基础工资和加班溢价分别列示。现金运营成本、SLA/未服务经济损失和总经济影响不会混成一个财务口径。
- 容量规划默认使用 `TAIL_APPEND_ONLY`：保留选中 V 的已有安排，只在路线尾部安置原未服务需求；这不是完整插入优化。每个方案都会复核技能、时间窗、旅行连续性、锁定、真实返程和加班上限。不可执行方案只保留诊断路线和违规，不输出正式收益或抵消天数。每班和每单成本会按受影响技师或工单数量计量。
- 风险仿真使用按 seed、trial、事件类型和实体编号派生的共同随机场景。页面分开显示突发事件发生概率与事件实际造成业务损害的概率；不同 V 使用相同参数时可以核对同一个场景集哈希。

每个新 V 都保存发布排程哈希和校验报告指纹。生成经营分析、打开报告或重新激活历史方案前，系统会再次核对完整覆盖、唯一性、技能、时间窗、旅行、锁定、返程、KPI、求解政策和场景快照。容量 A 的完整反事实路线与校验报告保存在独立证据记录中，不会只留下摘要。

当前只实现 `EX_ANTE_FROZEN_PLAN`（事前冻结计划分析）。场景已有开始或完成事件时，请求必须显式选择这个范围，结果会标明“不含实际执行、不代表剩余预测”并绑定当前执行水位。`INCURRED_ACTUAL`、`REMAINING_FORECAST` 和 `ACTUAL_PLUS_FORECAST` 返回稳定的未支持错误，不会用全日计划冒充当前预测。这些数值用于比较假设，不是财务结算或现场承诺。

内置场景包括：

- 今日调度：4 名技师、24 个工单
- 技能不足
- 时间窗冲突
- 突发工单重排
- 策略实验（中型）：8 名技师、60 个工单
- 策略实验（压力型）：12 名技师、100 个工单

## 主要目录

- `backend/scheduler.py`：基线、OR-Tools 排程、指标和局部重排
- `backend/decision.py`：整数分成本、容量 what-if 和固定 seed 风险仿真
- `backend/storage.py`：SQLite、数据修订、方案版本、经营分析和策略实验
- `backend/main.py`：FastAPI 接口和 HTML 报告入口
- `frontend/src/`：React 调度台
- `tests/`：算法、接口、迁移和并发测试
- `frontend/e2e/`：Playwright 主流程

## 求解状态

- `FEASIBLE`：已找到可执行方案，未证明全局最优。
- `TIME_LIMIT_FEASIBLE`：达到时限时已有可执行方案。
- `TIME_LIMIT_NO_SOLUTION`：达到时限时仍没有可执行方案。
- `NO_SOLUTION` / `INFEASIBLE`：未找到方案，或求解器已确认约束无解。
- `INVALID_MODEL` / `FAILED` / `CANCELLED`：模型、运行或取消状态。
- `OPTIMAL`：只在求解器明确返回最优性证明时使用。

未分配工单会给出原因码和处理建议。工单详情中的“开始服务”和“完成服务”会校验当前正式分配并写入执行事件；局部重排保留服务中的安排并排除已完成工单。系统仍不会根据计划时间猜测“已出发”或“已到场”。

## 检查

```bash
make test          # 后端与接口
make lint          # Ruff、Pyright、OpenAPI 与 TypeScript 静态检查
make audit         # Python 与前端生产依赖漏洞检查
make test-frontend # React 组件
make build         # TypeScript 和生产构建
make demo-check    # 基线、优化、锁定、突发单、重排、比较和报告
make benchmark-smoke # 决策模型与场景基准快速检查
make test-e2e      # Playwright 主流程和 200% 缩放
make verify        # 运行以上全部检查
```
